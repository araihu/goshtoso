# Product

## Register

brand

## Users

Goshtoso serves Go developers building server-rendered web applications who want
typed components, local runtime assets, and enough interactivity for real app
work without adopting a JavaScript application stack. Users are often evaluating
whether the library can replace copy-pasted UI snippets or a heavier frontend
toolchain, then returning to the docs and demo site while wiring components into
their own Go services.

## Product Purpose

Goshtoso exists to make interactive Go web interfaces feel practical, inspectable,
and shippable. It provides templ components, theme tokens, bundled CSS and
JavaScript, HTMX-friendly behavior, Alpine.js local state, and runnable examples
that show how server-rendered HTML can carry application UI. Success looks like a
developer understanding the model quickly, trusting the component API, and seeing
that the demo site is built from the same primitives they can import.

## Brand Personality

Go-native, practical, playful. The voice should feel technically grounded and
direct, with enough character to make the project memorable without turning the
documentation into a joke. Goshtoso can be colorful and a little opinionated, but
the product promise stays concrete: typed Go components, local assets, rendered
HTML, small client-side sprinkles.

## Anti-references

Do not make Goshtoso look like a generic SaaS landing page, a CDN-snippet gallery,
or a component catalog made from interchangeable icon cards. Avoid glossy
framework marketing, vague claims about productivity, and decorative AI-looking
patterns that are not connected to the Go-first product. Keep the Copacabana
gopher personality as a signal, not a gimmick that overwhelms technical trust.

## Design Principles

Practice what the library teaches: pages should be composed from real Goshtoso
components whenever possible, not screenshots or decorative substitutes.

Show the server-rendered model in use: prefer demos, fragments, example apps, and
themeable states over abstract promises.

Make local-first trust visible: bundled assets, no CDN dependency, and reproducible
Go workflows should be obvious without sounding defensive.

Balance utility with personality: keep docs scannable and component APIs clear,
while letting the brand feel distinct from neutral design-system catalogs.

Design for adoption paths: first-time visitors need quick orientation, while
returning users need predictable navigation, API details, and runnable examples.

## Accessibility & Inclusion

Target WCAG AA for public pages, component demos, and example apps. Preserve
keyboard access, visible focus states, semantic HTML, live-region behavior where
needed, color contrast across shipped themes, and reduced-motion alternatives for
animations. Avoid relying on color alone to communicate state, especially in
theme previews and data-heavy components.
